給 Android 開發者的 iOS 知識

Flutter 讓同一份 Dart 代碼跑在 iOS 上，但 iOS 版的建置、簽章、權限、原生串接，還是得照 Apple 的規則來。這一頁用 Android 的概念一一對照，說明一個 Kotlin 開發者第一次碰 iOS 時需要知道的事。原生代碼的部分用 Swift，並列在對應的 Kotlin 代碼旁邊。

一定要有 Mac。iOS App 只能用 Xcode 建置，Xcode 只能在 macOS 上執行。沒有 Mac 的團隊，可以用 macOS 的 CI 機器建置與上架，但開發和除錯時，還是很難不用 Mac。

依賴管理：Swift Package Manager 與 CocoaPods

說明

Android 的原生依賴由 Gradle 從 Maven 下載。iOS 有兩套工具：

  • Swift Package Manager（SPM）：Apple 官方的套件管理，整合在 Xcode 裡。目前版本的 Flutter 預設啟用（flutter config 的 enable-swift-package-manager 預設為開啟），plugin 的 iOS 原生代碼會以 Swift package 的形式加入專案。
  • CocoaPods：過去的主流，用 Podfile 宣告依賴、pod install 安裝。還沒支援 SPM 的 plugin，Flutter 會自動退回用 CocoaPods 處理，這時 ios/ 裡會出現 Podfile。

平常只要執行 flutter pub get 或 flutter run，Flutter 會處理好這兩套工具。需要自己介入的情況，多半是某個 plugin 要求提高 Deployment Target，或是 CocoaPods 的快取出問題（這時常見的解法是刪掉 ios/Pods 和 Podfile.lock 再執行一次）。

App 生命週期

說明

在 Flutter 裡不需要直接處理原生的生命週期，統一用 AppLifecycleListener 或 WidgetsBindingObserver 收到 AppLifecycleState。但兩個平台觸發狀態的時機不完全一樣：

Flutter 狀態AndroidiOS
resumedonResume 之後，可以互動scene 進入 active，可以互動
inactiveActivity 可見但失去焦點，例如分割畫面時操作另一個 App暫時失去焦點：來電、拉下控制中心、進入 App 切換畫面
hidden所有畫面都看不到了，即將進入 paused同左
pausedonStop 之後，在背景進入背景。iOS 很快就會暫停背景 App 的執行，要在背景工作必須申請特定的背景模式
detached引擎還在，但沒有任何畫面（例如最後一個 Activity 被銷毀）App 即將結束時，不保證會收到

最大的差別在背景執行：Android 可以用 WorkManager 或前景服務長時間在背景工作，iOS 則嚴格得多，只有音樂播放、定位、VoIP 這類特定用途能持續在背景執行，一般工作只能用 BGTaskScheduler 由系統決定何時執行。

簽章：跟 Android 差最多的地方

說明

Android 的簽章很單純：自己用 keytool 產生一個 keystore，所有版本都用它簽，裝置上不檢查是誰簽的。iOS 則由 Apple 掌控整個流程，連裝到自己的手機上測試都要簽章：

iOS 的東西是什麼Android 最接近的概念
Apple Developer Program付費會員（每年 99 美元），才能上架與使用推播等功能。只用個人 Apple ID 也能裝到自己的手機，但簽章 7 天後就會過期Google Play 開發者帳號（一次性費用）
憑證（Certificate）Apple 簽發給你的開發或發佈用憑證，私鑰存在你的 Mac 的鑰匙圈裡keystore 裡的 key，但由 Apple 簽發
App ID在 Apple 後台註冊的 Bundle Identifier，以及它開啟的功能（推播、Sign in with Apple…）applicationId
Provisioning profile把「憑證＋App ID＋可安裝的裝置清單＋功能」綁在一起的檔案。開發用的版本只能裝在登記過的裝置上沒有對應
EntitlementsApp 使用的功能清單（Runner.entitlements），必須和 provisioning profile 一致Manifest 裡的部分權限與功能宣告

實務上，在 Xcode 的 Signing & Capabilities 分頁勾選「Automatically manage signing」並選擇 Team，Xcode 會自動建立與更新憑證和 provisioning profile。第一次在實機執行 flutter run 前，先用 Xcode 開啟 Runner.xcworkspace 完成這一步。上架用的發佈簽章與 CI 上的簽章設定，留到第 8 章。

同一份 Flutter 代碼，在 iOS 上會有哪些不同

說明

Flutter 會自己繪製所有 UI，所以 Material 元件在 iPhone 上看起來還是 Material。不過有些行為會自動依平台調整，有些則需要你自己處理：

項目Flutter 的預設行為要注意的地方
返回iOS 沒有系統返回鍵。MaterialPageRoute 在 iOS 上會改用從右滑入的轉場，並支援從左邊緣滑動返回只能靠返回鍵離開的畫面（例如 Android 上沒有返回按鈕的頁面），在 iOS 上要自己放一個返回按鈕
捲動iOS 上預設是回彈效果（BouncingScrollPhysics），Android 是邊緣發光或拉伸效果通常不用處理
安全區域瀏海、動態島、底部的 home indicator 會遮住內容用 Scaffold 的 AppBar 時已經處理好；自己排版的畫面要用 SafeArea
平台風格元件Material 元件在兩個平台長得一樣想要 iOS 原生的外觀，可以用 Switch.adaptive、CircularProgressIndicator.adaptive 這類 .adaptive 建構子，或 cupertino 函式庫的元件
字型預設使用系統字型：Android 是 Roboto，iOS 是 San Francisco用自訂字型就會兩邊一致

要判斷目前在哪個平台，用 Theme.of(context).platform 或 defaultTargetPlatform，而不是 dart:io 的 Platform.isIOS：前兩者在測試時可以覆寫，也能在 Web 上使用。

這一章的 Swift 代碼怎麼確認可用

說明

這個 repo 沒有 iOS 專案，samples/ios_snippets/ 只放 Swift 原始碼。為了確保網頁上的 Swift 代碼真的能編譯，typecheck.sh 直接用 Flutter SDK 內附的 Flutter.xcframework 對它們做型別檢查，CI 也會執行：

flutter precache --ios
samples/ios_snippets/typecheck.sh

想在 iPhone 上實際執行第 6 章的範例，可以在 samples/native_bridge 執行 flutter create --platforms ios . 產生 iOS 專案，再把這些 Swift 檔加進 Runner，並讓 AppDelegate 實作 NativeBridgeAppDelegate 的內容。
