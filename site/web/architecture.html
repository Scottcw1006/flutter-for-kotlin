Flutter 在 Android 上怎麼運作

開始寫程式碼之前，先搞清楚一件事：用 Flutter 寫的 App，在 Android 上到底是什麼？簡單的答案是，它仍然是一個標準的 Android App，只是畫面不交給 Android 畫，而是由 App 自帶的 Flutter engine 自己畫。理解這一點之後，後面很多「為什麼 Flutter 要這樣做」的問題都會有答案。

它還是一個 Android App

說明

用 flutter create 建立的專案裡有一個 android/ 資料夾，裡面就是你熟悉的 Gradle 專案：AndroidManifest.xml、applicationId、minSdk、權限宣告、簽章設定都在原本的位置。差別只在 MainActivity：

  • setContent { } 是把 Compose UI 放進這個 Activity，Activity 本身仍然由你掌控。
  • FlutterActivity 會建立一個 FlutterEngine，執行 Dart 的 main()，然後把整個畫面交給 Flutter。你的 Dart 程式碼從 lib/main.dart 開始，Activity 這一層通常不用再動。
  • 整個 App 通常只有這一個 Activity。換頁是 Flutter 內部的事（第 4 章的導航），概念上就是 single-activity 架構加上 Navigation Compose。

這個 android/ 專案就是第 6 章串接原生功能的入口：要呼叫 Android SDK、使用既有的 Kotlin 函式庫，程式碼都寫在這裡。

三層架構

說明

把兩種 App 從上到下拆開來看：

  • Framework（Dart）：你每天打交道的部分，包含所有 widget、Material 與 Cupertino 元件、版面配置、動畫、手勢。它是一般的 Dart 原始碼，在 IDE 裡按住 Cmd 點進去就能讀。
  • Engine（C++）：負責繪圖（Impeller）、執行 Dart 程式碼、排版文字。它會被編譯成 libflutter.so，打包在你的 APK 裡。
  • Embedder（Kotlin / Java）：把 engine 接到 Android 上，負責建立 Surface、轉送觸控與鍵盤事件、處理生命週期、在 Dart 和原生程式碼之間傳訊息（第 6 章的 platform channel）。

Flutter 的 Material 元件是用 Dart 重新實作的，不是 Android 的 Material Components。所以同一個 FilledButton 在 Android 和 iOS 上看起來完全一樣，Android 系統升級也不會改變它的外觀。

畫面是怎麼畫出來的

說明

其實 Compose 已經走了一半的路：它不會替每個 Composable 建立一個 Android View，而是全部畫在同一個 AndroidComposeView 的 canvas 上，只是繪圖、文字排版仍然交給 Android 的 RenderNode 和 HWUI。

Flutter 則走完全程：它只向 Android 要一塊 Surface（FlutterView 裡的 SurfaceView），每一個像素都由 engine 自己決定。每一幀的流程是 build → layout → paint → 合成 → raster：前四步在 Dart 端完成，最後由 Impeller 用 Vulkan 或 OpenGL 把畫面送到 GPU。

這個設計帶來幾個你在 Android 開發中不會遇到的現象：

現象原因與對應做法
Android Studio 的 Layout Inspector 只看得到一個 FlutterView畫面裡根本沒有 Android View。改用 Flutter DevTools 的 Widget Inspector。
TalkBack 照樣能讀出內容Flutter 另外建立一棵 semantics tree，再橋接到 Android 的無障礙 API。需要補充說明時用 Semantics widget，相當於 Compose 的 Modifier.semantics。
要嵌入地圖、WebView 這類原生元件比較麻煩原生 View 要透過 Platform View 合成進 Flutter 畫面，有額外成本，第 6 章說明。
外觀在不同 Android 版本、不同廠牌上都一致元件和字型渲染都由 Flutter 自己處理，不受系統主題和廠商客製化影響。

Dart 程式怎麼執行

說明

Dart 程式碼在開發與發佈時的執行方式不同，這也是 Flutter 開發體驗的關鍵：

模式Dart 怎麼跑用途
debugJIT，在 Dart VM 裡執行開發。支援 hot reload：把改過的程式碼注入正在執行的 VM，畫面立刻更新，狀態也會保留。效能不代表正式版。
profileAOT 編譯，保留效能分析工具量測效能、找掉幀。要在實機上跑。
releaseAOT 編譯成原生機器碼（libapp.so）上架。沒有 VM 直譯也沒有 JIT，啟動快、執行快。

debug 模式下捲動卡卡是正常的，不要拿 debug 版判斷效能。這跟 Compose 在 debug build 比較慢是同樣的道理，但 Flutter 的差距更明顯。

執行緒

Dart 的程式碼跑在 isolate 裡，每個 isolate 是單執行緒加上一個 event loop，彼此不共享記憶體。你的 UI 程式碼跑在主 isolate；Flutter 3.29 起，它在 Android 上直接跑在 App 的主執行緒，繪圖則由另一條 raster 執行緒負責。

這代表 Dart 沒有 Dispatchers.IO 這種「切換執行緒」的概念：網路和檔案 I/O 本來就是非同步、不會卡住 UI；真正吃 CPU 的運算才需要丟到另一個 isolate。第 2 章的非同步會詳細對照 coroutines。

APK 裡有什麼

說明

把 release 版 APK 用 Android Studio 的 APK Analyzer 打開，會看到這些東西：

檔案內容
classes.dexembedder、plugin 的 Kotlin/Java 程式碼，以及你的 MainActivity
lib/arm64-v8a/libflutter.soFlutter engine
lib/arm64-v8a/libapp.so你的 Dart 程式碼，AOT 編譯後的機器碼
assets/flutter_assets/在 pubspec.yaml 宣告的圖片、字型等資源

因為要帶著 engine，最小的 Flutter App 會比 Compose 的 hello world 大幾 MB。上架時用 App Bundle（AAB）讓 Google Play 依裝置 ABI 分發，就不會把每種 CPU 架構的 .so 都裝到使用者手機上，第 8 章說明。

BuildContext 名字很像 Context，但完全是兩回事。它不能拿來存取系統服務或資源，只代表「這個 widget 在樹中的位置」，用來往上找主題、導航器等資料。第 5 章會詳細說明。

依賴管理：build.gradle 與 pubspec.yaml

左邊是本 repo 的 Compose 範例模組，右邊是待辦 App 的 pubspec.yaml：

  • 新增套件用 flutter pub add 套件名稱，它會改 pubspec.yaml 並下載，相當於加一行 implementation 再 Gradle sync。
  • dev_dependencies 對應 testImplementation 這類只在開發時用到的依賴。
  • 版本寫法 ^6.0.0 表示「6.0.0 以上、7.0.0 以下」。實際解析出的版本記錄在 pubspec.lock，App 專案要把它 commit 進版控。
  • uses-material-design: true 讓 App 打包 Material 圖示字型，Icons.xxx 才能顯示。
