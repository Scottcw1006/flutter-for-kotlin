測試與除錯

前面幾頁一直提到「測試時可以 override 掉 Repository」，這一頁就實際替待辦 App 寫測試。Flutter 的測試有一個讓 Android 開發者羨慕的地方：UI 測試不需要模擬器，幾秒鐘就跑完。後半頁說明除錯工具，以及怎麼讀懂 Flutter 的錯誤訊息。

測試種類對照

說明
AndroidFlutter需要裝置嗎
JUnit 單元測試（src/test）單元測試：test()都不需要
Compose UI 測試（src/androidTest）Widget 測試：testWidgets()Compose 需要裝置或 Robolectric；Flutter 不需要，在電腦上直接畫出 widget 樹
Espresso、UI Automator 的端對端測試整合測試：integration_test 套件都需要

單元測試與 widget 測試都放在 test/，用 flutter test 執行。待辦 App 的 5 個測試，扣掉第一次編譯的時間，在筆電上不到一秒就全部跑完；同樣的 Compose UI 測試則要先把 test APK 安裝到模擬器上。

Notifier 的單元測試

說明

測試 ViewModel 時，要把 Dispatchers.Main 換成測試用的 dispatcher，再用 Turbine 收集 StateFlow。測試 Notifier 則是建立一個 ProviderContainer，用 overrides 換掉 Repository，完全不需要 widget：

KotlinRiverpod
建構子注入假的 RepositoryProviderContainer.test(overrides: [...])，測試結束時自動釋放
Dispatchers.setMain(...)不需要，Dart 只有一條執行緒
Turbine 的 test { } 開始收集container.listen(provider, ...)
awaitItem()await container.read(provider.future)
測試 dispatcher 推進await container.pump()

先 listen 再讀取。Riverpod 3 會暫停沒有人監聽的 provider，只用 container.read(todoListProvider.future) 的話，這個 Future 會一直等不到結果，測試在 30 秒後逾時。這和 stateIn(WhileSubscribed) 的 StateFlow 沒有收集者就不會啟動，是同樣的道理。

這個測試第一次執行時就失敗了，抓到一個真的 bug：網站 demo 與測試用的 InMemoryTodoRepository，原本先送出目前的清單、之後才開始監聽變更，兩者之間的修改會被漏掉。正式 App 用的 drift 沒有這個問題，所以畫面上從來沒出錯過。修正後的 watchAll() 改成先監聽、再送出。

Widget 測試

說明

Widget 測試用 pumpWidget 放入要測的 widget，再用 find 找元件、tester 操作，概念與 Compose UI 測試幾乎一一對應：

Compose UI 測試Flutter widget 測試
composeTestRule.setContent { }await tester.pumpWidget(...)
onNodeWithText("…")find.text('…')
onNodeWithContentDescription("…")find.byTooltip('…')、find.bySemanticsLabel('…')
onNodeWithTag("…")find.byKey(const ValueKey('…'))
performClick()、performTextInput()tester.tap(...)、tester.enterText(...)
assertExists()、assertDoesNotExist()expect(finder, findsOneWidget)、findsNothing
自動等待 UI 閒置要自己呼叫 await tester.pump() 或 pumpAndSettle()
mainClock.advanceTimeBy(…)await tester.pump(duration)

最大的差別是時間由你推進：Compose 的測試規則會自動等待重組與動畫結束，Flutter 則是在你呼叫 pump() 時才畫下一幀。pumpAndSettle() 會一直推進到沒有動畫為止；如果畫面上有無限循環的動畫（例如轉圈的 CircularProgressIndicator），它會逾時，這時改用 pump()。

整合測試

說明

要在真的裝置上、用真的 drift 資料庫跑完整流程，用 Flutter SDK 內附的 integration_test 套件。測試程式碼的寫法和 widget 測試完全相同（同樣是 testWidgets 與 find），只是放在 integration_test/ 資料夾，用 flutter test integration_test 在連接的裝置上執行。它也能在 Firebase Test Lab 上跑，地位相當於 Espresso 測試。

讀懂 Flutter 的錯誤

說明

Flutter 的 build() 或排版發生錯誤時，App 通常不會崩潰，而是把出錯的那一塊換成錯誤畫面，其他部分照常運作。這跟 Android 一拋例外就閃退很不一樣，所以也要注意 release 版不會讓錯誤「看起來很明顯」：

看到的畫面代表什麼
紅底黃字的錯誤畫面debug 版 build() 拋出例外。release 版會換成一塊灰色區域，使用者只會覺得畫面怪怪的
邊緣的黃黑斜紋overflow：子元件超出了 constraints 給的空間（第 3 章），console 會印出「A RenderFlex overflowed by N pixels」。只在 debug 版顯示
Vertical viewport was given unbounded height在 Column 裡直接放 ListView（第 3 章）
setState() called after dispose()非同步工作結束時，畫面已經關掉了。在 await 之後先檢查 mounted（第 2 章）
Null check operator used on a null value對 null 用了 !，相當於 Kotlin 的 !! 拋出 NPE
No ProviderScope found忘了在 runApp 最外層包 ProviderScope（第 4 章）

錯誤訊息的第一段通常就寫了原因和解法，最後還會列出「The relevant error-causing widget was」，點擊就能跳到出錯的那一行程式碼。

把錯誤送到 Crashlytics 等服務：因為很多錯誤不會讓 App 閃退，要同時攔截兩個地方：FlutterError.onError（框架內的錯誤，例如 build() 失敗）與 PlatformDispatcher.instance.onError（其他未處理的非同步例外）。firebase_crashlytics 的設定說明就是設定這兩個。release 版用了 --obfuscate 的話，記得上傳符號檔（第 8 章）。
