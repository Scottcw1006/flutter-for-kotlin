App 骨架與主題

開始寫畫面之前，先看一個 Flutter App 最外層長什麼樣子：flutter create 產生了哪些檔案、runApp 和 MaterialApp 扮演什麼角色、Scaffold 的各個欄位對應 Compose 的哪裡，以及主題與深色模式怎麼設定。之後每一頁的範例，都是放在這個骨架裡面。

flutter create 產生了什麼

說明

執行 flutter create --org com.example my_app 會產生一個可以直接執行的專案。平常會碰到的檔案：

檔案Android 對應用途
lib/main.dartMainActivity.ktDart 程式的進入點 main()，所有 Dart 程式碼都放在 lib/ 底下
pubspec.yamlbuild.gradle.kts 的 dependencies套件依賴、版本號、字型與圖片等資源宣告
pubspec.lockGradle 的 dependency lock實際解析出的套件版本。App 專案要 commit
analysis_options.yamlLint／detekt 設定Dart 靜態分析與 lint 規則，flutter analyze 會讀取
test/src/test/單元測試與 widget 測試（第 4 章「測試與除錯」）
android/、ios/整個 Android 專案各平台的原生專案。改 App 名稱、權限、簽章時才需要動（第 1、6、8 章）
build/、.dart_tool/build/、.gradle/建置產物與快取，不進版本控制

加入套件用 flutter pub add 套件名稱，它會改好 pubspec.yaml 並下載，相當於在 Gradle 加一行 implementation 再 sync。

從 setContent 到 runApp

說明

Compose 在 Activity 裡呼叫 setContent，最外層通常包一個 MaterialTheme，再放 Scaffold。Flutter 的結構幾乎一樣，只是入口變成 main() 裡的 runApp：

ComposeFlutter說明
setContent { }runApp(widget)把最外層的 UI 交給框架
MaterialThemeMaterialApp 的 themeMaterialApp 不只提供主題，還包含導航（Navigator）、語系、App 標題等設定，相當於 MaterialTheme 加上 NavHost 的外框。用 go_router 時改成 MaterialApp.router（第 4 章）
isSystemInDarkTheme()themeMode: ThemeMode.system同時提供 theme 與 darkTheme，由 themeMode 決定用哪一個
Material Theme Builder 產生的 ColorSchemeColorScheme.fromSeed / colorSchemeSeedFlutter 內建「從一個種子色產生整套配色」
dynamicLightColorScheme(context)dynamic_color 套件Android 12 以上依桌布取色
Scaffold(topBar = …)Scaffold(appBar: …)TopAppBar 對應 AppBar
bottomBarbottomNavigationBar放 NavigationBar
floatingActionButtonfloatingActionButton完全相同
snackbarHost ＋ SnackbarHostStateScaffoldMessenger.of(context).showSnackBar()Flutter 不必自己準備 host，MaterialApp 已經提供 ScaffoldMessenger
content 的 padding 參數bodyFlutter 的 body 已經排在 AppBar 下方，不需要自己套用 padding

範例的 FAB 外面多包了一層 Builder。原因是 ScaffoldMessenger.of(context) 要從 context 往上找，而 _SkeletonAppState.build 的 context 在 MaterialApp 的「外面」，找不到。這是 BuildContext 代表「在樹中的位置」造成的，第 5 章的BuildContext一節有完整說明。實務上，Scaffold 通常會放在另一個 widget 類別裡，就不會遇到這個問題。

在元件裡使用主題

說明

Compose 用 MaterialTheme.colorScheme.primary 讀取主題，Flutter 用 Theme.of(context).colorScheme.primary，文字樣式則是 Theme.of(context).textTheme.titleLarge。範例的 SeedPicker 就是這樣讀取的，所以切換主題時它會自動更新。

  • 不要寫死顏色：跟 Compose 一樣，盡量從 colorScheme 取色，深色模式才會正確。
  • 統一調整元件外觀：ThemeData 有 filledButtonTheme、cardTheme、inputDecorationTheme 等欄位，可以一次改掉所有同類元件的預設樣式，不用每個地方各自設定。
  • 自訂的設計 token：品牌色這類 Material 沒有的值，用 ThemeExtension 掛在 ThemeData.extensions 上，再用 Theme.of(context).extension<MyColors>() 讀取，角色就像自訂的 CompositionLocal。

專案結構

說明

Flutter 沒有規定 lib/ 的資料夾結構。中大型 App 常見的是依功能分資料夾（feature-first），每個功能底下再分層，跟 Android 的多模組架構想法相同：

lib/
├── main.dart              // runApp、ProviderScope、MaterialApp
├── app/                   // 路由、主題等全 App 共用的設定
├── features/
│   ├── todo/
│   │   ├── data/          // Repository、drift 資料表、API
│   │   ├── domain/        // 資料類別、商業邏輯
│   │   └── presentation/  // 畫面、Notifier
│   └── settings/
└── shared/                // 共用的 widget 與工具

本教學的 todo_app 只有一個功能，所以直接用 data/、screens/、widgets/ 三個資料夾。Dart 沒有 Gradle 模組那種編譯期的隔離，資料夾之間的依賴方向要靠團隊自己約定；需要強制分隔時，可以把功能拆成獨立的 Dart 套件，用 path 依賴引入，就像第 6 章的 todo_module 引入 todo_app 一樣。

挑選套件與 lint 設定

說明

Flutter 生態系大量依賴 pub.dev 上的第三方套件。挑選時可以看這幾個指標：

指標代表什麼
Pub pointspub.dev 自動評分：文件、靜態分析、平台支援、依賴是否過時
Verified publisher發佈者經過網域驗證，例如 dart.dev、flutter.dev、google.dev 是官方維護
Flutter FavoriteFlutter 團隊挑選的高品質套件
平台標籤是否支援 Android、iOS、Web 等你需要的平台
最後發佈時間、GitHub issue是否還有人維護。原生相關的套件尤其要注意，太久沒更新常會跟新版 Android Gradle Plugin 不相容

flutter pub outdated 會列出可以升級的套件，作用類似 Gradle 的 versions plugin。

lint 方面，flutter create 已經在 analysis_options.yaml 引入 flutter_lints。團隊可以再打開更嚴格的規則，例如第 5 章提到的 prefer_const_constructors：

include: package:flutter_lints/flutter.yaml

linter:
  rules:
    - prefer_const_constructors
    - prefer_final_locals
