Key 與 const

上一頁說過，父層重建時，Element 會拿新的 widget 跟舊的比對：型別相同、key 也相同，就沿用原本的 Element 和 State。這一頁的兩個主題都建立在這條規則上：Key 決定「哪個新 widget 對應哪個舊 Element」，const 則讓 Flutter 發現「widget 根本沒變」，直接跳過重建。

沒有 Key 時，State 跟著位置走

說明

第 3 章的列表已經遇過這個問題，這裡用最簡單的例子再看一次：兩個方塊的顏色存在各自的 State 裡，建立時決定一次，A 是紅色、B 是藍色。按「交換」把它們的順序對調：

  1. 沒有 key 時，Flutter 依位置比對：新的第一個是 ColorTile('B')，舊的第一個 Element 也是 ColorTile，型別相同，於是沿用。結果是 Element 和紅色的 State 都留在第一格，只把 widget.label 更新成 B。
  2. 加上 ValueKey(label) 後，Flutter 依 key 比對，發現 B 的 Element 在第二格，就把整個 Element 連同 State 移過來。

Compose 的規則一樣：同一個呼叫位置、沒有 key() 時依順序配對 remember 的值，用 key(label) { } 包起來就會跟著資料走。

需要 key 的情況其實不多：同一層有多個同型別、而且有狀態的子元件，又可能被新增、刪除或重新排序時才需要。最常見的就是列表的每一列。

Key 的種類

說明
Key用途Compose 對應
ValueKey(id)最常用。用資料本身的 id 或值當 key，以 == 比較items(key = { it.id })、key(id) { }
ObjectKey(obj)用物件的身分（同一個實例）比較，適合沒有 id 的物件以物件本身當 key
UniqueKey()每次建立都不同。用來強制重建、丟掉舊的狀態，例如 AnimatedSwitcher 每次都要播動畫時改變 key() 的值
GlobalKey整個 App 唯一，可以從外部拿到某個 widget 的 State，或讓 widget 在樹中移動時保留狀態。最常見的用法是 Form：formKey.currentState!.validate()沒有直接對應；Compose 會把狀態提升出來，或使用 movableContentOf

不要在 build() 裡寫 key: UniqueKey()：每次重建 key 都不同，Flutter 會每次都丟掉舊的 Element 和 State，等於讓這個元件永遠記不住任何東西。GlobalKey 也要存在 State 的欄位裡，不能每次 build 都建立新的。

const：讓 Flutter 跳過重建

說明

父層重建時，如果新的子 widget 跟舊的是同一個物件，Flutter 就知道設定沒變，直接跳過整個子樹的 build()。const 剛好保證這件事：相同的 const 運算式在整個程式裡只會有一個實例。

這裡有一個跟 Compose 很不一樣的地方：

  • Compose 比較參數是否相等：RecomposeCounter("參數沒變的子元件") 的參數每次都相等，就算是新的字串物件，也會被跳過。
  • Flutter 比較的是 widget 物件是否為同一個：非 const 的 BuildCounter(label: '非 const 子元件') 參數完全沒變，但每次 build() 都 new 了一個新物件，所以每次都會重建。Widget 沒有覆寫 ==，Flutter 也不會逐一比對欄位。

所以在 Flutter 裡，能寫 const 的地方就寫，效果相當於 Compose 自動幫你做的 skip。實務上的建議：

  • 自己寫的 widget，建構子都宣告成 const（所有欄位都是 final 就可以）。
  • 在 analysis_options.yaml 開啟 prefer_const_constructors 規則，IDE 會提示哪裡可以加 const。這條規則預設沒開，這份教學的 demo 就沒有開。
  • 不要為了 const 硬改架構：重建一個小 widget 的成本很低。真正有效的優化，是把會變動的部分拆成小 widget，讓重建範圍變小。Flutter DevTools 的 Performance 頁可以看到每個 widget 被重建的次數。
