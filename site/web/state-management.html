ViewModel 與狀態管理

Android 有官方的標準答案：ViewModel 加 StateFlow，再用 Hilt 注入依賴。Flutter 官方沒有規定，社群有好幾套做法。這份教學用 Riverpod，因為它一個套件同時處理「畫面狀態」和「依賴注入」，對應關係最直接。

AndroidRiverpod
ViewModelNotifier、AsyncNotifier、StreamNotifier
MutableStateFlow 加 asStateFlow()state：只有 Notifier 自己能改，外面只能讀
collectAsStateWithLifecycle()ref.watch(provider)
onClick = viewModel::incrementref.read(provider.notifier).increment()

Notifier 與 ViewModel

說明
  • Notifier 的 build() 回傳初始狀態，方法裡直接改 state，相當於 _count.update { }。
  • NotifierProvider 是一個全域變數，但它不是單例的狀態：狀態實際存在 App 最外層的 ProviderScope 裡。所以測試時可以換掉，每個 ProviderScope 也都有自己的一份。
  • 要讀取 provider，widget 改繼承 ConsumerWidget，build() 會多一個 WidgetRef ref 參數。

ref.watch 和 ref.read 的分工：在 build() 裡讀取要顯示的資料用 watch，它會在值改變時重建 widget；在 onPressed 這類回呼裡呼叫方法用 read，它只讀一次、不訂閱。在 build() 裡用 read 會讓畫面不更新，在回呼裡用 watch 則會報錯。

兩邊的組織方式有一個差別。Compose 的慣例是在畫面這一層 collect 一次，再把值和回呼一路傳給子元件。Riverpod 則讓任何一個 widget 都能直接訂閱 provider，不用一層層傳下去。後者比較方便，但可以重複使用的小元件仍然建議用參數傳值，讓它不依賴特定的 provider。

衍生狀態

說明

在 ViewModel 裡用 map 或 combine 從一個 Flow 算出另一個，Riverpod 的寫法是：寫一個新的 Provider，在裡面 ref.watch 它依賴的 provider。依賴的值一變，它就會自動重新計算，沒變就沿用快取。

  • 不需要 stateIn、SharingStarted 這類設定，Riverpod 會自己管理訂閱與快取。
  • 只想在某個欄位變動時才重建，可以用 ref.watch(provider.select((s) => s.欄位))，效果類似 map { }.distinctUntilChanged()。待辦 App 的詳細頁就用它來挑出單一筆待辦。

非同步狀態與 AsyncValue

說明

Android 慣例是自己定義 UiState sealed interface 來表示載入中、成功、失敗。Riverpod 內建了 AsyncValue，FutureProvider、StreamProvider、AsyncNotifier 的狀態都是它，直接用 switch 比對就好。

  • weatherProvider 裡 ref.watch(simulateErrorProvider)，所以開關一變就會自動重新載入，不用另外寫「開關改變時呼叫 refresh」的代碼。
  • ref.invalidate(provider) 會讓它重新執行，對應 ViewModel 的 refresh()。
  • 重新載入時，舊的請求如果比較晚回來，它的結果會被自動丟掉。Kotlin 版要自己保存 Job 並 cancel()，才能避免舊結果蓋掉新結果。
  • 重新載入期間，AsyncValue 會保留上一次的資料，並把 isLoading 設為 true。想顯示轉圈就先檢查 isLoading；想讓舊資料留在畫面上，就直接比對 AsyncData。

Riverpod 3 預設會自動重試失敗的 provider。拋出 Exception 時，它會以 200 毫秒起跳、逐次加倍（最長 6.4 秒）的間隔重試，最多 10 次。重試期間狀態是「帶著錯誤的載入中」，isLoading 一直是 true，所以畫面會持續轉圈，重試用完才變成 AsyncError。對網路請求這通常是好事；但如果錯誤要馬上讓使用者看到，就像這裡一樣傳入 retry: (retryCount, error) => null 關掉它。拋出的是 Error（程式錯誤）時則不會重試。

依賴注入：Hilt 與 Riverpod

說明

Riverpod 的 provider 本身就是依賴注入。一個 provider 要用到另一個，就在裡面 ref.watch 它；要替換實作，就在 ProviderScope 用 overrides。

HiltRiverpod
@Inject constructor(private val api: UserApi)Provider((ref) => UserRepository(ref.watch(userApiProvider)))
@Module、@Binds 介面綁定實作介面型別的 provider，在 ProviderScope(overrides: [...]) 提供實作
測試時用 @TestInstallIn 替換 module測試時在 ProviderScope 用不同的 overrides
@Singleton一般的 provider（跟著 ProviderScope 一直存在）
@ViewModelScoped、ViewModel 被清除.autoDispose：沒人監聽時自動釋放，用 ref.onDispose 清理資源

待辦 App 就是這樣做的：todoRepositoryProvider 只宣告介面，真正的實作在 main() 決定。App 用 drift，測試和這個網站用記憶體版本。

實作主線：待辦清單的 Notifier

說明

待辦 App 原本把清單放在畫面的 State 裡，現在改成三層：TodoRepository 負責存取資料、TodoListNotifier 負責畫面狀態與操作、TodoListScreen 只負責顯示，跟 Android 建議的架構一致。

  • StreamNotifier 的狀態直接來自 Repository 的 Stream：資料庫一變，畫面就跟著更新，對應 repository.watchAll().stateIn(...)。
  • 新增、勾選、刪除只呼叫 Repository，不用手動更新清單，因為 Stream 會把新資料送回來。
  • remainingCountProvider 是衍生狀態，標題列的「剩幾項」就讀它。
