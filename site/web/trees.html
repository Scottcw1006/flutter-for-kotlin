三棵樹與 BuildContext

前面一直說「widget 是不可變的設定、每次重建都會產生新的」，那 State 存在哪裡？BuildContext 又是什麼？答案是 Flutter 其實同時維護三棵樹。Compose 也有類似的分層，只是藏在編譯器和 runtime 裡；Flutter 則讓你直接碰到它們，所以值得花一頁弄清楚。

Widget、Element、RenderObject

說明
  • Widget：你寫的東西，只是一份描述。建立成本很低，所以每次 build() 都重新產生沒關係。
  • Element：widget 在樹中的「實體」，長期存在。StatefulWidget 的 State 就掛在它身上；你拿到的 BuildContext 其實就是 Element。
  • RenderObject：負責排版（第 3 章的 constraints 規則就在這一層運作）和繪製。只有真正會畫東西的 widget 才有。

對應到 Compose：Composable 函式的呼叫相當於 widget；Compose runtime 用 slot table 記住的組合結構（remember 的值就存在那裡）相當於 Element 樹；LayoutNode 則相當於 RenderObject。

父層重建時，Element 會拿新的 widget 跟舊的比對：型別相同、key 也相同，就沿用原本的 Element 和 State，只更新設定；否則就丟掉舊的、建立新的。下面的 demo 讓你直接看到這件事：

BuildContext 是「在樹中的位置」

說明

Theme.of(context)、Navigator.of(context)、MediaQuery.sizeOf(context) 這些呼叫的意思都是：「從 context 這個位置往上找，最近的那個 Theme（或 Navigator）是誰」。所以重點在於你手上的 context 是哪一個位置的。

  • build(context) 的 context 是這個 widget 自己的位置，在它 build() 回傳的 Theme 外面，所以往上找不到這個紫色的 Theme。
  • Builder 會在當下的位置建立一個新的 context，從那裡往上找就找得到。另一個做法是把底下的部分抽成獨立的 widget，它自然有自己的 context。
  • Compose 沒有這個問題：LocalAccent.current 寫在 CompositionLocalProvider 的 lambda 裡，執行時就已經在 Provider 裡面了。

常見的同類錯誤：在建立 Scaffold 的同一個 build() 裡呼叫 Scaffold.of(context)，或在建立 ProviderScope 的同一層讀 provider，都會找不到。解法也都一樣：用 Builder 或拆出新的 widget。

InheritedWidget 與 CompositionLocal

說明

Theme.of、MediaQuery.of 背後都是 InheritedWidget：把一個值提供給整棵子樹，底下任何一層都能用 of(context) 取得，作用跟 CompositionLocal 一樣。

  • dependOnInheritedWidgetOfExactType 除了找值，還會登記依賴：值改變時，只有登記過的 widget 會重建，這跟讀取 CompositionLocal 的 composable 會被重組是同一個機制。
  • updateShouldNotify 決定「怎樣才算改變」，相當於 compositionLocalOf 的相等性比較。
  • 實務上很少直接寫 InheritedWidget：Riverpod 的 ProviderScope 和 Theme 都已經幫你包好了。理解它，是為了看懂 of(context) 在做什麼。

State 的生命週期

說明

State 跟著 Element 一起存在，它的生命週期方法對應 Compose 的 effect：

Flutter State時機Compose
initState()第一次加入樹，只會呼叫一次remember { }、DisposableEffect(Unit) 的開頭
didChangeDependencies()依賴的 InheritedWidget 改變時（第一次也會呼叫）讀取的 CompositionLocal 改變導致重組
build()每次需要重建時重組
didUpdateWidget(old)父層傳入新的 widget（參數可能變了）LaunchedEffect(參數) 因 key 改變而重新執行
dispose()從樹中移除，之後不會再用onDispose { }

需要清理的資源（AnimationController、TextEditingController、StreamSubscription）在 initState 或欄位初始值建立，在 dispose 釋放。Compose 的 effect 會自動清理，Flutter 要自己記得。

為什麼要抽成 Widget，而不是方法

說明

第 3 章提過，build() 太長時要抽成新的 widget 類別，不要抽成回傳 Widget 的方法。了解三棵樹之後就能說明原因：

  • 沒有自己的 Element：方法只是把一段 widget 樹貼回父層的 build() 裡。父層任何一點變動，這段都會跟著重建；獨立的 widget 則可以用 const 跳過，或只在自己的資料變動時重建。
  • 沒有自己的 context：方法用的是父層的 context，上一節的 Theme 問題就是這樣發生的。
  • 不能有自己的狀態：方法裡沒辦法放 State。

Compose 沒有這個問題，因為每個 @Composable 函式本身就是一個可以單獨重組的範圍。Flutter 裡對應「一個 composable 函式」的，是一個 widget 類別，不是一個方法。
